# Full Browser-Based QA Verification Protocol

**Scope:** Exhaustive verification of every UI element, every function, every edge case, and every failure path — conducted in a real browser, with the log stream monitored continuously throughout.

**Status:** For vendor execution. Report per-case results, not aggregate claims.

---

## 0. Ground Rules — Read Before Starting

### 0.1 This is a floor, not a ceiling

**You wrote this code. We did not.** Our knowledge of this system is limited to what we can see in the browser and read in the logs. This protocol covers what *we* know to ask about — which is necessarily incomplete.

Therefore, this document is the **minimum** required, not the full scope. You are expected to additionally test:

- Every code path, branch, and error handler you know exists but that is not mentioned anywhere below.
- Every assumption, shortcut, `TODO`, stub, hardcoded value, or "good enough for now" decision made during implementation across all milestones.
- Every integration point whose failure mode has never actually been exercised (only mocked in tests).
- Anything where the automated test suite mocks or stubs something that would behave differently against the real service.
- Anything you know to be fragile, incomplete, or untested — including things never raised in any review round.
- Any interaction between features that were built in different phases and may not have been tested together.

**If you know of a weak spot we have never asked about, test it and report it.** Surfacing a problem yourself is the expected behavior here, not a failure. Concealing a known weak area because nobody asked is the failure.

### 0.2 "Expected Result" is our best guess, not the specification

Every "Expected Result" in the tables below is written from outside the system, based on what has been described to us across this project. **You know the actual intended behavior far better than we do** — you wrote it. Where our stated expectation is wrong, incomplete, or doesn't match what the system was actually designed to do, do not just mark it FAIL and stop there:

- Note what the **correct** expected behavior actually is, and why.
- Test against that correct understanding, not blindly against our possibly-wrong description.
- Flag the mismatch explicitly so the record is accurate going forward.

We would rather be corrected than have you silently test against a wrong assumption because it's what we wrote down.

### 0.3 Additional changes requested directly, outside this document

Separately from this protocol, we have also communicated a number of enhancement and change requests directly to you in conversation — items we do not have full visibility into ourselves, that are not enumerated here. Those requests are still in scope for this verification pass:

- Confirm every direct request we've made to you — whether or not it appears in this document — has actually been implemented.
- Verify each one the same way as everything else here: in the browser, with logs monitored, not by assumption.
- If any such request was ambiguous, was interpreted a particular way, or was only partially implemented, say so explicitly rather than marking it done.

### 0.4 Execution rules

- Keep two things open side by side for the entire session: the dashboard, and a live tail of `storage/logs/shorts_engine.log` (or the `/logs` page).
- Record log output for **every** action, not just failures. Silence in the log when an action was performed is itself a finding.
- Note wall-clock time of each action so it can be correlated against log timestamps.
- If actual behavior differs from "Expected" even slightly, record **FAIL** with the difference described. Do not interpret near-misses as passes.
- Test in at least two browsers (e.g. Edge and Chrome) for anything involving video playback, modals, or live-update polling.
- Do not fix issues silently mid-run. Record them, finish the protocol, then report the full list.
- Do not mark a case as passed based on a code reading, a plausible assumption, or a unit test that exercises the same code path. Browser-verified means browser-verified.
- If a case cannot be executed (missing credential, missing config, environment limit), say so explicitly and ask for what is needed. **Report untested as untested.**

### 0.5 Log a suggestion for every case, not just failures

For **every single row** in every table below — pass, fail, or not applicable — use the fourth column to note anything worth improving: a better architectural approach, a more robust way to handle that case, a UX refinement, a performance improvement, an edge case adjacent to this one that should also be handled, or a design decision you'd reconsider now that it's built and tested end to end. A row that passes cleanly can still have a "this could be better because..." note. Leave it blank only if there is genuinely nothing to add.

## 9. Visual, Layout, Branding & Cross-Cutting UI

For each item, note pass/fail **and** any enhancement worth suggesting, same as the tables above.

- Every page: no invisible or low-contrast text anywhere (muted text, table headers, badges, help text, placeholders, disabled controls).
- Logo renders in navbar; favicon appears in browser tab on **every** page.
- Navigation highlights current page correctly on all pages.
- All flash banners dismissible; do not persist incorrectly after navigation.
- Resize window to mobile width on every page — no horizontal overflow, no overlapping controls, tables scroll rather than break layout.
- Long values (long video titles, long filenames, long error strings) do not break table layout anywhere.
- **Every button in the app clicked at least once** — confirm none are dead, mislabeled, or produce no visible feedback.
- Tab-key navigation reaches interactive controls sensibly; no keyboard trap in the video modal.
- Browser console: **zero uncaught JavaScript errors** on any page, during any action.
- Empty states: with zero channels, zero clips, zero logs — every page renders a sensible empty message, not a blank or broken view.

## 10. Live Processing Run — Four Assigned Videos

Process these four through the full pipeline, monitoring the log continuously. Run one at a time first, then note behavior when overlapping runs are attempted.

```
1. tphyf6Y3OcY  — "How Radical Islam Is Advancing in America"
2. HErzoaoos_s  — "Iran Just Tightened Its Grip on Global Oil"
3. 2nw59PPCa1c  — "Steve Bannon's Next Grift Is Here"
4. DsWqPUWouRc  — "Why All of Ed Sheeran's Openers Just Quit"
```

### 10.1 Record per video

- Wall-clock duration of **each stage**: download, transcription, forced alignment, clip selection, per-clip render, quality gate.
- Source video duration and word count, so processing time can be assessed relative to content length.
- Number of candidates selected; each one's timestamp range, score, and whether it fell inside configured duration bounds.
- **Whether clip selection used the real LLM or the heuristic fallback** — and for each LLM call, which provider/model actually served it.
- Every quality-gate outcome with the specific reason for each pass/fail (technical / framing / semantic).
- Total AI calls, total failures/retries, quota state before and after.
- Peak disk usage added; total output size per video.
- Any warning or error line in the log, even if the run ultimately succeeded.

### 10.2 Then assess overall

- **Editorial quality:** watch every generated clip end to end. Does each stand alone, open on a strong hook, end at a sensible point? Flag any clip starting or ending mid-sentence.
- **Reframing quality:** is the speaker actually kept in frame, or does the crop drift, jitter, or lose the subject?
- **Caption accuracy and timing:** transcription errors, desync, or text colliding with YouTube UI dead zones.
- **Audio:** loudness consistency across clips, SFX placement appropriateness, no clipping or abrupt cuts.
- **Consistency across the four** — note whether quality varies by source content type, and how.
- **Throughput:** total time from source video to publish-ready clips, and where the real bottleneck is.
- **Enhancements:** for anything observed in this run — editorial, technical, or architectural — note what could be improved, same as the tables above.

> **Note:** These four include politically charged and news-commentary content. Flag anything where an automatically selected clip strips context in a way that materially changes the meaning of what the speaker said. That is a pipeline quality finding (bad cut-point selection) worth reporting — not an editorial judgment on the source material.

## 11. Reporting Format

Report per-case, not summarized:

1. A table of **every** case ID with PASS / FAIL / NOT APPLICABLE, a one-line note, **and** any suggested enhancement (per §0.5) — carry the fourth column through into the report, don't drop it.
2. For every FAIL: what was done, what was expected (including any correction per §0.2), what actually happened, and the **exact log excerpt** from that moment.
3. **A separate section confirming every direct request made outside this document (§0.3)** — listed individually, each with its own verification status.
4. **A separate section for everything you tested beyond this document** (per §0.1) — what you chose to test, why, and what you found.
5. **A consolidated list of every suggested enhancement/architecture improvement**, pulled together from the fourth column across all tables, so it can be reviewed as its own backlog rather than only buried per-row.
6. A separate list of anything encountered that this protocol did not anticipate.
7. The four-video performance data from §10, with stage timings.
8. The complete verbatim log file from the whole session, committed to disk — not summarized in chat.

> **Standing requirement:** If anything requires input only we can provide (a credential, a config value, a decision, an asset), state it explicitly and ask for it directly. Do not proceed on assumptions or placeholders. Do not report something as working without it being independently demonstrable.
